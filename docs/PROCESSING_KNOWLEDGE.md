# 四档处理规则与观测

评估器把四档地图投影到同一张处理表。每行是一条原子规则，由站型、资料、操作、输入规格和输出规格组成。重复站点归在同一站型下。规则编号在一张地图的固定版本内有效，分析按 `processing_table_sha256` 和 `rule_id` 关联。跨地图比较使用规则结构与观察结果。同名站型在不同地图上可以有不同能力。

| --- | ---: | --- | --- |
| Capulin Easy | 8 | 一种资料对应一个站型，原始资料直接处理 | 本站型完整支持列表 |
| Nessie Normal | 24 | 每种资料有多个匹配站型，原始资料直接处理 | 本站型完整支持列表 |

Hard 61601 候选已经使用与 Lunatic 相同的中间规格引擎。因此，同一难度也要按设计版本识别规则及反馈。当前地图各自保存固定分配，评估表复用同一结构和口径。未来可先定义中间规格和兼容边，再由各档挑选可用规则、委托链和反馈范围，分别验证每张地图。

## 从审计记录观察复用

1. 每个交付反馈记录它明确披露的规则及事件编号。给出完整支持列表的反馈可以同时披露多条规则。只给出单次处理结果的反馈仅披露该成功转换。
2. 每项必需操作列出合法规则和在本委托开始前已披露的子集。未尝试也保留为一次机会，且首试正确为假。
3. 每次实际处理记录产物是否符合该段目标。产生另一套有效规格会披露实际规则，同时该段首试计错。
4. 首试使用了此前披露的同一规则时，记录本次决策与对应的早期反馈事件。若此前只披露了另一个合法站型，可以分别统计是否有可用的先前经验，以及首试是否选择了此前披露的那条规则。

评估表只供审计和论文分析。模型在游戏中按原接口探索，观察到的是各版本规定的反馈。论文可用规则编号串起一条证据链：较早委托的交付事件、后来委托要求的目标、首次处理选中的站型与规格。要验证模型收到自己写下的记忆正文，需另用回执匹配到决策前的请求，推断内部因果仍需独立的干预实验。

四组的全部首试分子和分母均复现了原审计。匹配反馈按实际收到的信息计数，包括探索中偶然看到的有效处理结果。 [Hard 61601 封存摘要](assets/hard-target60-retain/summary.json) · [Lunatic v4.2 封存摘要](assets/lunatic-goal-switch-expanded-pilot/summary.json) · [双组全量核验摘要](assets/night-full-calibrations/summary.json)

例如 Hard 61601 的 `R0053` 表示 T 型站可将 `material-2` 的原始资料编目成 `F-2`。T3 的事件 390 交付了这条规则。T4 的事件 483 记录了模型在 T2 站的首次编目，实际产物是该委托所需的 `F-2`。两个事件用同一个规则编号核对，站点编号 T2 则能定位地图上的具体行动。

## 导出

在项目根目录运行。输出是评估材料，储存在非公开的工作目录。现有游戏规则、提示词、地图接口与封存结果均沿用自己的版本。

```powershell
python -m operations.processing_knowledge --catalog --output .runs/processing-table.json
python -m operations.processing_knowledge --archive <已核验的封存包> --output .runs/processing-observations.json
```

`--design` 可选择候选设计文件，`--archive` 可重复指定相互独立的归档。导出程序核对读取的审计、地图、事件清单和事件块，沿用原有审计口径复核必需操作的分子和分母。若归档带有旧版指标，原始指标仍可与评估表并列使用。该命令只派生记录，保留一份原始归档即可。
