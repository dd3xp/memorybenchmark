# GA 逐步执行对照

这组实验只改变原生 GA 的游戏动作粒度：每次模型响应最多尝试一个游戏动作，收到反馈后再请求模型。原有批量脚本执行继续作为基线。

运行入口增加 `--action-policy single`，默认 `batch` 保留原生执行行为。策略随运行记录冻结，恢复时不能切换。逐步模式目前限于原生 GA；上游工具列表和记忆实现保持原样。

## 执行边界

- `move`、`inspect`、`process`、`submit`、`abandon` 都消耗本轮唯一的动作机会，包括被游戏拒绝的尝试。
- `read`、文件和记忆工具不受动作限制。
- 配额由宿主维护，每次成功的模型响应后恢复。多个工具调用、脚本循环或新建客户端连接不能重置配额。
- 同一响应中的额外动作不执行，单独记录 `action_policy_rejected`，不增加游戏路程或操作数。客户端中止当前脚本，并把已接受动作的最新公开反馈交给模型。
- 游戏失败、模型预算耗尽和基础设施故障继续按原协议区分。只有已识别的基础设施故障允许有界恢复。

## 本轮比较条件

沿用批量基线的上游 GA `e4d956f`、`gpt-5.6-luna`、low 推理设置、Easy20 类型站地图、既定隐藏世界和工作进程种子。每会话上限仍为 100 次执行阶段调用、6 次整理调用、3,600 秒和 88 次游戏操作。新运行从原版基础记忆重新开始，20 项保留主线与 19 项当前任务清除记忆探针均使用独立的新会话。

唯一新增的 Agent 说明是每轮只执行一个游戏动作及边界反馈的处理方式；原有任务、记忆提醒和整理机会不变。脚本联调中的人工标记与路线只用于软件测试，不能进入真实运行的基础记忆。

比较任务成功、首次选站、重复探查、道路距离、SOP 的读取时机、模型调用和 token 用量。调用次数增加本身不算记忆收益。两种策略会产生各自的实际学习历史；同一世界的一次试跑不能确定总体因果效应。

软件校验：`python -m scripts.check_ga_single_action --reference-run <原始GA运行目录> --output <独立校验目录> --runtime <WSL运行环境>` 使用脚本响应驱动真实原生 GA，不调用模型网关。
